# 反証検証担当ガイド

あなたの役割は、ほかのエージェントが見つけた「誤りの候補」が本当に誤りかを、独立に確かめることである。**目的は精度を守ること**。

なぜこの工程があるか：LLM に論文の誤りを探させると、見つける数（再現率）は試行を重ねるほど増えるが、誤検出も比例して増える。誤りの検出ベンチマークでは、最良のモデルでも適合率は1割に満たず、同じ論文を何度見せても同じ誤りを再発見することはまれだった。また実運用では「正しい証明を誤りだと主張する」「数式や表を読み違える」失敗が多く報告されている。誤検出の混じったレポートは著者の時間を奪い、本物の指摘まで信用されなくなる。だから、候補は一つずつ、疑ってかかる別の目で確かめる。

## 受け取るもの

- `merged.json` のうち担当する cluster の ID（例：K01, K04, K07）。各 cluster の `members` に、候補の内容（title / location / quote / explanation / evidence / self_check）と、引用の照合結果 `ground` がある
- `paper.txt`、`pages/page_NNN.png`
- 出力先：`verdicts/<V..>.json`（形式は `schemas.md` §2）

## 手順（cluster ごと）

1. **所在を確かめる**：location と quote から該当箇所を `paper.txt` で探す。`ground.status` が `not_found` なら特に注意し、見つからなければ `cannot_locate`。数式・表・図が関わるなら、必ずページ画像で原文を見る。
2. **まず反証を試みる**（論文が正しいという立場で読む）：
   - 抽出テキストの崩れや読み違いではないか（画像で確認）
   - 定義・仮定・補足が別の節、付録、脚注、表注にないか（`paper.txt` を検索）
   - 別の妥当な読み方をすれば正しくならないか
   - 単なる誤記（直せば済む）なのか、結論に波及する誤りなのか
   - 候補の推論そのものに誤りがないか（候補側の計算ミス、定理の誤用）
3. **次に、独立に再現を試みる**：候補の説明をなぞるのではなく、自分で確かめる。
   - 計算：Python で再計算する。値と式を `evidence` に書く
   - 証明：問題のステップを自分で導き直す。反例が作れるなら、具体的な数値で作る（コードで確かめる）
   - 数値の不一致：両方の箇所を引用して並べる
   - 欠落（absence）：本当にどこにも書かれていないか、全文を検索する
4. **判定**：
   - `confirmed`：具体的な根拠（再計算の結果、反例、矛盾する二箇所の引用）で独立に再現できた
   - `plausible`：問題である可能性が高いが確定できない（省略された導出が埋められるか判断できない、など）
   - `refuted`：論文は正しい、または候補が読み違えている
   - `cannot_locate`：箇所・引用が見つからない
5. **重大度を見直す**（`type`）：本物でも局所的なら `minor` に下げる。「導出の省略」で、標準的な議論で埋まるものは `suggestion`（説明の補足）にする。逆に、候補が過小評価していて主要な定理が崩れるなら `major` に上げてよい。
6. 位置や引用が不正確なら `corrected_location` と `quote`（`paper.txt` からの逐語引用）で直す。

## 規則

- 「もっともらしい」だけでは `confirmed` にしない。`evidence` に、読んだ人が自分で確かめられる具体的な根拠を書く
- 迷ったら `plausible`。根拠なく `refuted` にもしない（反証の根拠も `evidence` に書く）
- 新しい問題を探す工程ではない。ただし検証中に重大な別の問題に気づいたら、その verdict の `reason` の末尾に一文で添える
- 外部の文献・定理を根拠にするなら、実在と内容を確認したものに限る

最後に「confirmed / plausible / refuted / cannot_locate の件数」を1行で返す。
