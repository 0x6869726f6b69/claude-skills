# 提出前の点検項目

下書きを渡す前に上から順に確かめる。引っかかった項目は直してから渡し、直せないもの（ユーザーの事実が必要なもの）は `[TODO]` として一覧に残す。

## 時期

- [ ] 議論期間はまだ開いているか。改訂 PDF の期限は過ぎていないか。終わっていれば最初に伝えたか。

## 事実

- [ ] 改訂・追加実験・数値は、すべてユーザーが伝えた事実か。推測で書いた結果が無いか。
- [ ] ユーザーの事実のうち、誤りの疑いがあるもの（先行研究の記述、「標準的な仮定」の根拠など）に `[TODO: 確認]` と理由を付けたか。
- [ ] 「最終版で追加します」は、ユーザーが実施を決めたものだけか。
- [ ] 「追加しました」（済み）と「追加します / camera-ready で追加します」（予定）を区別しているか。
- [ ] 改訂 PDF を出せない投稿先（NeurIPS 2025 以降など）で「改訂版をアップロードしました」と書いていないか。
- [ ] 節・図・表・行番号は改訂版のものか。未確定なら `[TODO: Sec. X]`。
- [ ] 査読者が認めた強みは、その査読者が実際に書いた語か。言っていない賛辞を書いていないか。強みに付けた査読者 ID は正しいか。

## 構成

- [ ] General Response の `G1, G2, …` と、個別返信での参照（"see G2"）が一致しているか。
- [ ] 共通の懸念は本当に 2 人以上が挙げたものか。1 人だけの懸念を General Response で長く扱っていないか。
- [ ] General Response を置けない投稿先で、他の返信への参照に頼っていないか（各返信が単独で読めるか）。
- [ ] 文字数制限を守っているか（下書きごとに数えた値を書く）。
- [ ] 冒頭 3 文で「何を変えたか」が分かるか（謝辞だけで 1 段落使っていないか）。

## トーン

- [ ] 謝辞は 1–2 文に収まっているか。"insightful" "valuable" "constructive" などの形容詞を 1 文に 3 つ以上重ねていないか。
- [ ] 謝罪の多用（"We apologize for ..." の繰り返し）が無いか。誤りを認めるのは 1 回、具体的に。
- [ ] 誤解の指摘を "The reviewer misunderstood" のように相手の責任にしていないか。"We realize this was not clear in the original submission; we have clarified ..." の形にしているか。
- [ ] スコアの変更を頼む文は最大 1 回、控えめな形か（"we would be grateful if you would consider updating your assessment"）。強い要求（"we ask you to raise the score"）になっていないか。
- [ ] 同じ定型文（"We thank the reviewer for ..."）を全返信で繰り返していないか。

## 匿名性・規則

- [ ] 著者名・所属・謝辞・身元が分かるリポジトリやリンクを書いていないか。
- [ ] リンクを禁止する投稿先で URL を書いていないか（匿名リポジトリでも禁止の年度がある）。
- [ ] 他の査読者の ID・コメントを引用するとき、公開範囲の設定と矛盾しないか（ICLR は公開、ほかは査読者・AC のみの場合がある）。
- [ ] 投稿先が LLM の利用について規定を設けている場合、それに反していないか（文章の推敲としての利用は多くの会議で許されるが、年度ごとに確認）。
