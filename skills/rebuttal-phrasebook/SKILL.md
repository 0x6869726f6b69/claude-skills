# Rebuttal Phrasebook：実際の査読対応から集めた典型文で rebuttal を書く

査読への返信の「型」の部分（冒頭の謝辞、査読者が認めた強みの確認、改訂の要約、共通の懸念への回答の導入、結び、期間中の追加メッセージ）を、OpenReview で公開された実際の査読対応から集めたフレーズで組み立てる。中身（反論・追加実験の結果）はユーザーの事実だけで書き、型の部分だけを典型文で補う。

用語：
- **Opening Statement**：返信の冒頭の段落（謝辞・査読者が認めた強み・何を変えたかの予告までの 2–4 文）。全員向けの欄がある投稿先では General Response の最初の段落、無い投稿先では各返信の最初の 1–2 文になる。ユーザーが GR とは別の短い最初の投稿として欲しい場合は、それ単体で出す。
- **General Response（GR）**：全査読者・AC に向けた 1 本の返信。Opening Statement に続けて、改訂の要約・共通の懸念への回答・結びを含む。

ユーザーに渡すもの（`<ws>/rebuttal_drafts.md`）：
1. **Opening Statement** の案（2–3 種類：標準・簡潔・字数制限用）
2. **General Response** の下書き（投稿先が全員向けの欄を持たない場合は、各返信の冒頭に入れる短い Opening と共通の懸念の書き方）
3. 査読者ごとの返信の **書き出しと結び**（査読者ごとに、その査読者が挙げた強みと懸念に合わせる）
4. 必要なら **追加メッセージ**（リマインド、お礼、AC 向けの要約）
5. 使ったフレーズの言い換え表（頻度・採択やスコア上昇との関係・ニュアンスの日本語解説）
6. `[TODO]` の一覧（ユーザーが埋める数値・節番号・事実）

以下、`<skill_dir>` はこの SKILL.md があるディレクトリ、`<ws>` は作業フォルダ（査読ファイルと同じ場所、無ければ作業ディレクトリ）。

## 参考資料

- `references/phrasebook.md`：**本体**。働き（move）ごとの典型文、型（スケルトン）、データの統計。下書きの前に必ず読む。
- `references/venue_formats.md`：投稿先・年度ごとの形式（General Response の有無、文字数、改訂 PDF）。
- `references/checklist.md`：提出前の点検項目（よくある失敗）。
- `references/data_stats.md`：フレーズ集の元になった集計の要約と、データの出典・限界。
- `scripts/mine_openreview.py`：集計を作り直すスクリプト（任意。約 0.9 GB のデータが必要）。

## 1. 入力を集める

1. **査読コメント**：貼り付け・テキスト・PDF・スクリーンショットのどれでもよい。OpenReview のリンクだけを渡された場合は、ページの本文を貼ってもらうか保存してもらう（OpenReview は自動取得にボット判定をかけていることがあり、それを回避しない）。
2. **投稿先と年度**（例：ICLR 2027、NeurIPS 2026、ICML 2026、ジャーナル名）。
3. **やったこと・やること**：改訂の内容、追加実験とその結果の数値、反論の要点。ここに無い事実は書かない。
4. **欲しい部分**：既定は 1–3（Opening / General Response / 書き出しと結び）。4 は頼まれたときだけ。

足りないものは質問ツール（AskUserQuestion など）でまとめて 1 回だけ聞く。無ければチャットで聞く。結果の数値が未確定なら、聞き直さず `[TODO: 数値]` にして進める。

## 2. 投稿先の形式を確かめる

`references/venue_formats.md` を読み、その年度の形式を Web で確認する（Author Guide / FAQ / Dates / OpenReview の入力欄の説明）。確かめた URL と日付は出力に書く。確認できなければ、その旨を書き、表の情報で進める。

**まず議論期間がまだ開いているかを確かめる。** 終わっていれば、下書きを作る前にそのことをユーザーに伝える（AC 宛ての非公開コメントなど、まだ書ける欄があればそれも伝える）。

- 全員向けの欄がある（ICLR、NeurIPS 2023–2024 など）→ General Response を 1 本書き、個別返信から `G1` などで参照する。
- 無い（NeurIPS 2025 以降、ICML など）→ Opening を 1–2 文に縮めて各返信の冒頭に入れ、共通の懸念は各返信の本文で書く。
- 文字数制限 → 下書きごとに文字数を数えて書く（`python -c "print(len(open('x.txt',encoding='utf-8').read()))"` など）。

## 3. 査読を読み解く（review map）

下書きの前に、次の表を作業メモとして作る（出力にも短く載せる）。

| 査読者 | スコア / 確信度 | 認めた強み（査読者の言葉を 2–6 語で） | 主な懸念 | 誤解の可能性 |
| --- | --- | --- | --- | --- |

- 2 人以上が挙げた懸念を **共通の懸念** `G1, G2, …` にまとめる（General Response で答える候補）。1 人だけの懸念は個別返信に回す。
- 別々の査読者の似た懸念（例：通信量と実行時間）は、**1 つの答えで両方に答えられるときだけ** 1 つの G にまとめる。答えの中身が違う、または片方が未対応なら分けておく。
- 強みは、査読者が実際に書いた語を短く引用する（例：*novel*, *well-written*, *extensive experiments*）。言っていない褒め言葉を作らない。強みを挙げた査読者の ID を控える。
- 誤解に見える指摘は、本文のどこを読めば分かるかを控える（「誤解です」と書くのではなく、説明を足す形で答えるため）。
- ユーザーの事実の中に、誤りの疑いがあるもの（先行研究についての記述、「標準的な仮定」という主張など）があれば控えておき、下書きでは `[TODO: 確認]` を付けて理由を日本語で書く。黙って直さない。

## 4. 型を選ぶ

`references/phrasebook.md` の「スケルトン」から投稿先と状況に合う型を選ぶ。既定は次の順で、データ上いちばん多い並びに沿っている。

1. 宛名（任意）→ 2. 謝辞 → 3. 査読者が認めた強み（ID つき）→ 4. 改訂と追加実験の要約（箇条書き、変更箇所の示し方）→ 5. 共通の懸念 `G1…`（見出しつき）→ 6. 個別返信への案内 → 7. 結び（疑問があれば答える）

状況による調整（「厳しい」の目安：査読者の過半数が、その会議の尺度の採択ライン未満。ICLR・NeurIPS の 10 点尺度なら 6 = 採択ライン付近）：
- 厳しい査読 → 強みの確認は 1 文以内（強みを挙げた査読者がいなければ省く）。GR の大部分を改訂の列挙と共通の懸念への回答にあてる。
- 好意的な査読 → 強みの確認は 1 文で十分。長い謝辞は逆に読みにくい。スケルトン D（短い GR）も候補。
- 誤解が多い → `phrasebook.md` 2.8（貢献の再確認・誤解への説明）の型を 3 の後に 1–2 文入れる。
- 文字数制限が厳しい → 1, 3, 6 を削り、2 と 7 を 1 文ずつにする。
- 実験が期間内に終わらない → `phrasebook.md` 2.12 の型を使う。最終版で足すと約束するかはユーザーが決める。

## 5. 下書きを作る

1. 各 move について、`phrasebook.md` の典型文から 2–3 案を選び、review map の事実で埋める。スロット `[...]` は必ず埋めるか `[TODO]` にする。
2. 本文（反論・結果）はユーザーの事実だけで書く。**実施していない実験、まだ無い数値、していない改訂を書かない**。「追加します」と「追加しました」を区別する。
3. 型の文は、同じ表現を何度も使わない（"We thank the reviewer" を全返信で繰り返さず、言い換え表から変える）。
4. トーン：丁寧・具体的・短く。謝罪や過度な賛辞（"We deeply apologize", "extremely insightful" の連発）は避ける。スコアの変更を直接頼む文は、使うなら最後に 1 回、控えめな形で（`phrasebook.md` の注意を参照）。
5. 匿名性：著者名・所属・身元が分かるリンクを書かない。投稿先がリンクを禁じていれば URL を書かない。
6. 英文の下書きはそのまま貼れるようにコードブロックに入れ、統計（例：「"we are encouraged" を含む GR 778 件、採択 60%」）とニュアンスの解説は、そのすぐ下の日本語の表かメモに書く。英文の中に統計を混ぜない。統計は相関であり、使えば採択されるという意味ではないことを一度明記する。件数の少ない数字（`phrasebook.md` で「n 少」）は目安と書く。
7. 査読者ごとの書き出しと結びには、各懸念にどこで答えるか（本文・G 番号・節番号）を日本語の短いメモで添える。

## 6. 点検して渡す

`references/checklist.md` で点検する（事実と主張の一致、`G` 番号の参照の整合、文字数、匿名性、トーン、`[TODO]` の残り）。直したら `<ws>/rebuttal_drafts.md` に保存し、チャットでは次を短く伝える。

- 議論期間が開いているか（終わっていれば最初に）
- 選んだ型とその理由（1–2 行）
- Opening Statement の推奨案（そのまま貼れる形）
- `[TODO]` の数と主なもの（特に、ユーザーの事実に誤りの疑いがあるもの）
- 投稿先の形式を確認できたか（URL）

英語の下書きに、ニュアンスの日本語解説を添える。ユーザーが英語だけを望めば解説は省く。

## フレーズ集を作り直す（任意）

フレーズ集は `scripts/mine_openreview.py` で作った。新しい年度のデータで作り直したい、または特定の言い回しの実例を見たいときだけ使う。データ（Hugging Face の `Jasonpicky/openreview_raw`、ODC-By、約 0.9 GB）は同梱していないので、**ダウンロードの前にファイル名・サイズ・出典をユーザーに伝えて許可を得る**。

```bash
python <skill_dir>/scripts/mine_openreview.py files                      # ファイル一覧とサイズ
python <skill_dir>/scripts/mine_openreview.py download <data_dir>        # 許可を得てから
python <skill_dir>/scripts/mine_openreview.py analyze <data_dir> -o <out_dir>
python <skill_dir>/scripts/mine_openreview.py search <data_dir> "we thank all reviewers" -n 5
```

`search` で見た実例は言い回しの確認に使うだけにし、他の著者の文章をまとめて写さない（フレーズ集に載せているのは、多数の論文で共通に使われる定型句と、それをもとに書き起こした型だけ）。

## 注意点

- 典型文は「型」であって中身ではない。査読者が読みたいのは具体的な回答と変更箇所で、型の文を増やしても説得力は上がらない。
- 統計はすべて相関。強い論文ほど丁寧な General Response を書き、スコアも上がりやすい、という交絡がある。
- OpenReview の自動取得がボット判定で止められても、回避しない。ユーザーに本文を貼ってもらう。
