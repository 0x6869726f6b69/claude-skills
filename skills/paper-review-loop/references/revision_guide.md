# 改訂ガイド（著者側）

目的は、査読で指摘された問題を原稿の上で誠実に解決し、より強く説得力のある論文にすること。査読者のスコアを上げること自体は目的ではない。主張と証拠を一致させ、読者が納得できる原稿にすれば、評価は結果としてついてくる。

目次：0 捏造の禁止 / 1 トリアージ / 2 書き方 / 3 著者TODO / 4 response.md / 5 時間配分 / 6 コードとデータがある場合

---

## 0. 捏造の禁止（最優先）

この原稿は実在の研究である。存在しない実験結果・数値・図・データ・引用・証明を書けば研究不正となり、ユーザーに深刻な害を与える。次を守る。

- **新しい実験数値を作らない**。表に存在しない数値を足さない。既存の数値を変えない（原稿内の別の箇所に正しい値が示されている誤植の修正だけは可）
- **実行していない実験を「行った」と書かない**。「〜を確認した」「〜でも同様の傾向が見られた」のような、裏付けのない記述も同じ
- **引用は、実在が確実なものだけ**にする。既存の参考文献リストにあるもの、または著者・年・会議まで確実に分かっているもの。不確かなら `\authortodo{Cite work on ... (e.g., ...)}` とする
- **証明は、自分で厳密に導出・検証できた場合だけ**追加する。できなければ `\authortodo`
- **実験設定の詳細**（ハイパーパラメータ等）は、原稿のどこかに書かれているか、そこから明らかに導ける場合だけ書く。不明なら `\authortodo`

新しい結果が必要な指摘（`fixable_by_revision: no`、および `partial` の一部）は、§3 の著者TODOとして扱う。

## 1. トリアージ

`issues.json` のうち `status` が `open` / `partially_resolved` のものを、次の順で処理する。

1. Major かつ `yes`
2. Major かつ `partial`（本文でできる部分）
3. Rebuttal 質問のうち、原稿の内容で答えられるもの（答えを本文に反映する）
4. Minor かつ `yes`
5. Major / Minor かつ `no` → 主張の調整と著者TODO化
6. 「その他の細かい点」（誤字など）

指摘の種類ごとの、本文でできる対応：

| 指摘の種類 | 本文でできる対応 |
|---|---|
| 主張が証拠を超えている | 主張を証拠の範囲に合わせる（例："state-of-the-art" → "outperforms FedAvg and FedProx in our setting"）。成り立つ条件を明記する |
| 新規性・差分が不明確 | Introduction と Related Work で最近接研究との差分を明示する。性質の比較表（前提、通信量、クライアント側の状態の有無など。原稿内や確実な知識で確認できる事実だけ）を加える |
| 理論の仮定が強い | 仮定を明記し、その現実性、緩和できる可能性、既存研究の仮定との比較を Remark として論じる。仮定と実験設定が食い違うなら正直に書く |
| 証明の欠落・省略 | 厳密に書けるなら付録に追加。書けなければ著者TODO |
| 実験が足りない | 新しい数値は作らない。(a) 既存の結果で答えられる部分は整理し直して明示する、(b) 主張を現在の証拠に合わせる、(c) 必要な実験を該当箇所に `\authortodo` で示し、著者TODOにプロトコルを書く |
| 再現性情報の欠落 | 原稿内に散らばった情報を付録の表などに集約する。無い情報は著者TODO |
| Privacy の主張 | 脅威モデルを明記し、保証の範囲を正確に書く（例："we do not provide a formal privacy guarantee"）。追加で共有する情報のリスクを Limitations で論じる |
| スケーラビリティ | 計算量・通信量のオーダーを解析的に導出できるなら記載する。実測は著者TODO |
| 明確さ・記法 | 書き直し、定義の追加、図表の説明の改善 |

一つの改訂が別の箇所と矛盾しないかを確認する。Abstract・Introduction・Conclusion の主張は本文の変更に合わせて必ず更新する（本文で主張を弱めたのに Abstract に強い主張が残っている、というのは典型的な失敗）。

## 2. 書き方

- **著者の貢献の核を保つ**。手法そのものを変えない。新しい貢献を作らない
- 原稿の言語（英語論文なら英語）、文体、記法、テンプレートを保つ
- **ページ数**：本文のページ数を元より増やさない。投稿先の上限が分かっていればそれに従う。詳細は Appendix に回す
- 変更は、指摘に直接応えるものを優先する。原稿全体を書き直さない
- こまめにビルドし、最後に `build_pdf.py` でエラーと未定義参照がゼロであることを確認する

### `\authortodo` マクロ

プリアンブルに無ければ追加する。

```latex
\usepackage{xcolor}
\newcommand{\authortodo}[1]{{\color{red!70!black}\textbf{[AUTHOR TODO:} #1\textbf{]}}}
```

使い方：本文の該当箇所に、何が必要かを1文で書く。例：`\authortodo{Add results for $\alpha\in\{0.1,0.3,1.0\}$ and FEMNIST (see T1).}`。表のセルには `\authortodo{TBD}`。数値の代わりにもっともらしい値を入れてはいけない。

## 3. 著者TODO（`author_todo.md`）

本文だけでは解決できない課題を、著者がそのまま実行できる形で書く。ID（T1, T2, …）はラウンドをまたいで固定し、同じ課題を重複させない。

```markdown
# 著者TODO（新しい結果が必要な課題）

## T1（W1, Q1）非IIDの強さを変えた比較実験 — 優先度：高
- 目的：「異質性に頑健」という主張 C2 を検証する
- 実験：Dirichlet α ∈ {0.1, 0.3, 1.0} と FEMNIST。ベースライン FedAvg / FedProx / SCAFFOLD。
  クライアント100、参加率10%、seed 3つで平均±標準偏差
- 入れる場所：Sec. 5.2 の [AUTHOR TODO]、Table 3
- 結果が期待どおりでなかった場合：C2 を「α ≥ 0.5 の範囲で」に限定する
- 評価への影響：査読では、これが示されれば 3→4 とされている（r01 Q1）
- 推定コスト：<GPU時間など、分かる範囲で>
```

優先度は、査読の Justification と Rating で「判断を決めている」とされた指摘に関わるものを高くする。

## 4. response.md（ラウンドごと）

rebuttal / response letter の形で、各指摘への対応を書く。次のラウンドの査読者には渡さないが、ユーザーが改訂内容を追うために使う。

```markdown
# Response to Round <NN> Review

| ID | 対応 | 変更箇所 | 状態 |
|---|---|---|---|
| W1 | 主張 C2 を α=0.5 の設定に限定。追加実験は T1 として著者TODOへ | Abstract, Sec. 1 ¶3, Sec. 5.2 | 一部対応 |
| W2 | 脅威モデルを明記し、s_k の漏洩リスクを Limitations で議論 | Sec. 2.3（新設）, Sec. 7 | 対応 |

## 詳細

### W1：<指摘の要約>
- 対応：<何をどう変えたか>
- 未対応の部分と理由：<…>

## Rebuttal 質問への回答
### Q1
<原稿の内容で答えられる範囲で回答。新しい実験が必要なら「T1 で対応予定」と書く>
```

## 5. 時間配分

指定された `revise_by` の時刻までに、ビルドまで必ず終える。Major から順に処理し、時間が足りなければ Minor を残して終える（次のラウンドで対応できる）。途中で `python <skill_dir>/scripts/loop_state.py status <ws>` を見て残り時間を確認する。ビルドが通らない状態で時間切れになるのが最悪なので、大きな変更の後はその都度ビルドする。

## 6. コードとデータがある場合

ユーザーがコードとデータを渡していて、求められた実験が残り時間内（目安：数分〜十数分）に実行できるなら、実際に実行して本物の結果を報告してよい。その場合は実行コマンドと環境、乱数 seed を response.md に記録する。結果が出なかった、または途中で打ち切った実験について、推定値や外挿値を書いてはいけない。
