# Scientific core：守るものの定義と、変更の分類

このループは論文を「査読に耐える形」に近づけるが、研究そのものは著者のものである。研究課題・中心的なアイデア・主要な手法（scientific core）は原則として変えない。査読者がそれを変えるよう求めても、ループは自動では変えず、人間に確認する。このファイルは、core の書き出し方（§1）、変更の分類（§2）、人間への確認のしかた（§3）、主張の台帳（§4）を定める。

---

## 1. core の書き出し（`core/core.json` と `core/core.md`）

セットアップ時に、**元の原稿**から書き出す。各項目は原稿の逐語引用で裏付ける（言い換えで core をずらさないため）。

```json
{
  "title": "原稿のタイトル",
  "research_question": {"text": "研究課題（1〜2文、自分の言葉で）", "quote": "原稿からの逐語引用", "location": "Sec. 1 ¶2"},
  "central_idea": {"text": "中心的なアイデア・仮説・洞察", "quote": "…", "location": "…"},
  "main_method": {
    "text": "主要な手法・アプローチ・実験パラダイム",
    "defining_components": ["これを変えると別の手法になる構成要素"],
    "peripheral": ["実装の詳細・ハイパーパラメータなど、変えても手法の同一性は保たれるもの"],
    "location": "Sec. 3"
  },
  "claims": [
    {"id": "C1", "role": "main", "text": "主張（自分の言葉で）", "quote": "…", "location": "Abstract; Sec. 1 contributions",
     "evidence": ["Table 2", "Theorem 1"], "scope": "主張が及ぶ範囲（データ・設定・条件）"},
    {"id": "C2", "role": "supporting", "text": "…", "quote": "…", "location": "…", "evidence": ["Fig. 4"], "scope": "…"}
  ],
  "scope_boundaries": ["原稿が扱わないと明言していること"],
  "non_negotiables": ["人間が変えないと指定したこと（確認時に追記）"],
  "confirmed_by_human": false,
  "confirmed_at": null,
  "notes": ""
}
```

- `role: main` は、タイトル・Abstract・貢献の箇条書きに現れる主張。`supporting` はそれを支える副次的な主張。
- `core.md` は同じ内容を人が読む形にしたもの（5〜15行）。セットアップの確認で人間に見せる。
- 人間が修正したら `core.json` を直し、`confirmed_by_human: true` と日時を入れる。以後、反復の途中で core.json を変えてよいのは人間の判断（`r2r.py decide` で approve）があったときだけで、その変更は `notes` に記録する。

## 2. 変更の分類（L0〜L3）

すべての対応方針と変更に、core への影響の度合いを付ける。迷ったら一段上（より慎重な側）に分類する。

| 段階 | 内容 | 例 | 扱い |
|---|---|---|---|
| **L0** 表現 | 意味を変えない修正 | 誤字・文法、言い回し、記法の統一、文献の書式 | 自動 |
| **L1** 構成・提示 | 内容は同じで、見せ方を変える | 節の並べ替え、付録への移動、図の見やすさ・キャプション、定義の追加、最近接研究との差分の明示（実在を確かめた文献で）、Limitations の追加、投稿先が求める記載事項（事実だけで書けるもの） | 自動 |
| **L2** 主張と証拠の整合（core の範囲内） | core を保ったまま、主張を証拠に合わせる・証拠を足す | 主張の範囲を証拠に合わせて狭める、成り立つ条件を明記する、導出・証明の誤りを定理の役割を変えずに直す、既存の主張を検証する追加分析・追加実験、ベースライン・ablation・統計の追加、再現性の情報の追加、副次的な分析の変更 | 自動。ただし主張の変更は `claim_changes` に、実験は事前登録で記録 |
| **L3** core に触れる | 研究課題・中心的アイデア・主要手法・主要な主張を変える | 研究課題の変更、中心的な仮説の差し替え、主要手法の構成要素（`defining_components`）の追加・削除・置換、主要な主張（`role: main`）の削除または証拠を超える強化、主要な結果の土台であるデータ・評価手順の変更、投稿先に合わせて分野・貢献の打ち出し方を変える、タイトルの主張を変える、新しい貢献（新手法・新理論）の追加、著者・所属・謝辞・資金情報の変更 | **自動で変えない**。人間に確認（§3） |

### 境界の例

- **手法の記述の誤り**：コードで実際に実装されている内容に記述を合わせる修正は L2（コードで確かめ、記録する）。直すと手法そのものが変わるなら L3。
- **主定理の誤り**：主張を変えずに証明を直せるなら L2。仮定を強めて定理を弱めるが、主要な主張は保てるなら L2（`claim_changes` に記録し、本文でも明記する）。定理が救えず主要な主張が成り立たないなら L3。
- **追加実験が主張を否定した**：副次的な主張（`supporting`）なら、その範囲を狭める L2。主要な主張（`main`）なら L3 で、すぐに人間に確認する。結果を本文から隠すことは、どの段階でも許されない。
- **投稿先の scope に合わない**：打ち出し方を変えて合わせるのは L3。core を変えずに投稿先の読者にとっての意義を説明するのは L1。
- **批判された実験を削除する**：欠陥のある副次的な実験を、理由を記録して削除するのは L2。主要な主張を支える実験の削除は L3。不利な結果を批判から逃れるために消すことは禁止（健全性監査で落とす）。
- **査読者が新しい手法の追加を求めた**：L3（範囲の拡大で、検証もされていない）。Discussion で今後の課題として論じるのは L1。

## 3. 人間への確認

L3 の対応方針は `triage.json` で `action: "human"` にし、`human_question` に質問を書く。オーケストレーターがまとめて人間に聞く。

- 質問は AskUserQuestion などの質問ツールで、1回に最大4件まとめる。各質問に次を含める：何が指摘されたか（指摘 ID と要点）、なぜ core に触れるか、選択肢。
- 選択肢の典型：
  - `現状維持（推奨されることが多い）`：core は変えず、Limitations や response で指摘に向き合う
  - `変更を承認`：提案された変更の内容を具体的に書く（例：「主張 C1 を『非IIDの設定でも』から『α≥0.5 の設定で』に狭める」）
  - `保留`：判断を先送りし、最終レポートに残す
- 答えは `r2r.py decide <ws> --issue I003 --choice approve|reject|defer [--action edit|experiment|analysis] --note "<人間の言葉>"` で記録する。承認の場合だけ、その課題は次の改訂で自動で扱える。
- 人間がその場にいない（質問できない）場合は判断待ちのまま残し、他の作業を続ける。L3 の変更を推測で行わない。

## 4. 主張の台帳

主張（C1, C2, …）の変化を追う。主張の文言・範囲・強さを変えたときは、改訂担当・反映担当が `changes.json` の `claim_changes` に「主張・変更前・変更後・理由・課題 ID」を書く。最終レポートでは、元の主張と最終版の主張を並べた表を示す。主張が弱まったこと自体は失敗ではない。証拠に見合った主張にすることは、査読に耐える論文の条件である。
